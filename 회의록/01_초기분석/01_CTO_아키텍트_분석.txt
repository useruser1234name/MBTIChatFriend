1. 현재 아키텍처의 강점과 약점
================================================================================

[강점]

(1) 잘 설계된 도메인 모델과 관심사 분리
- 서버 측이 명확한 서비스 레이어로 분리되어 있음
  - chat_service.py: 대화 생성 + 호감도 계산
  - memory_service.py: 대화 요약/팩트 추출
  - vector_store.py: RAG 시맨틱 검색
  - story_state_store.py: 스토리 상태 관리
  - quality_service.py: 품질 평가
  - image_service.py: 이미지 생성
  - finetune_service.py: 파인튜닝 파이프라인
- 각 서비스가 단일 책임 원칙(SRP)을 잘 준수
- 근거: server/app/ 디렉토리 구조 전체

(2) 하이브리드 호감도 시스템 (chat_service.py:154-231, 234-289)
- 키워드 기반 + LLM 기반의 하이브리드 호감도 계산
- 부정문 처리(_is_negated), MBTI 궁합 가중치, 호감도 레벨별 차등 등 세심한 설계
- LLM 실패 시 키워드 fallback으로 안정성 확보

(3) 풍부한 캐릭터 시스템 (prompts.py)
- 16개 MBTI 성격별 상세한 프롬프트 (traits, style, speech_habits, thinking, emotional, quirks)
- 호감도 5단계별 행동 지침(AFFINITY_BEHAVIORS)
- MBTI 그룹별 Few-shot 예시
- 궁합 시스템(J/P 차원까지 포함)

(4) 다층 메모리 아키텍처
- L1: 대화 히스토리 (최근 20개, chat_service.py:466)
- L2: 대화 요약 + 팩트 추출 (memory_service.py, PostgreSQL 영속화)
- L3: RAG 시맨틱 검색 (vector_store.py, ChromaDB)
- L4: 에피소드 기억 (시간 가중 검색, vector_store.py:150-215)
- L5: 스토리 상태 (떡밥/약속/목표 추적, story_state_store.py)

(5) 품질 보장 시스템 (quality_service.py)
- 실시간 4축 평가 (MBTI일관성, 맥락적절성, 감정자연스러움, 참여품질)
- quick_score로 응답 전 게이트 (score < 0.4 시 재생성)
- 응답 다양성 추적 (bigram 기반, low_diversity_warning)
- 피드백 수집 (thumbs_up/thumbs_down)

(6) 안드로이드 클라이언트 아키텍처
- Hilt DI, Room DB, Retrofit + OkHttp 기반 표준 아키텍처
- SSE 스트리밍 + REST fallback 이중 통신 구조 (SseClient.kt)
- Firebase Auth 연동 (AuthInterceptor)

[약점]

(1) 동기 PostgreSQL 연결 (심각)
- postgres.py에서 psycopg.connect()를 매 쿼리마다 호출 (커넥션 풀 없음)
- get_conn()이 매번 새 커넥션 생성 후 닫음 (postgres.py:37-45)
- 동기 DB 호출이 async 서버에서 이벤트 루프를 블로킹
- 근거: postgres.py:30-45, 모든 fetchone/fetchall/execute 함수

(2) 인메모리 상태의 확장성 한계
- memory_service.py의 _conversation_summaries, _character_memories 딕셔너리
- image_service.py의 _tasks 딕셔너리
- finetune_service.py의 _models_cache
- 서버 인스턴스 간 상태 공유 불가 -> 수평 확장 불가능
- 근거: memory_service.py:18-19, image_service.py:69, finetune_service.py:23

(3) 콘텐츠 필터 비활성화 (보안 위험)
- content_filter.py의 check_content()가 항상 True 반환 (테스트 모드)
- get_safety_system_prompt()가 빈 문자열 반환
- chat_service.py에서도 입력/출력 필터가 주석 처리됨 (라인 357-365, 510-519)
- 근거: content_filter.py:19-30, chat_service.py:357-365

(4) SSE 스트리밍이 진정한 스트리밍이 아님
- main.py:275에서 _run_chat_pipeline()이 전체 응답을 먼저 생성한 후
  이미 완성된 replies를 하나씩 SSE로 전송 (유사 스트리밍)
- 실제 LLM 토큰 스트리밍이 아니므로 TTFB(Time To First Byte)가 높음
- 근거: main.py:263-304, chat_service.py:482-487

(5) 에러 핸들링의 일관성 부족
- 일부 서비스는 예외를 삼키고 기본값 반환 (memory_service.py)
- 일부는 HTTPException 발생 (main.py)
- 구조화된 에러 응답 모델이 없음
- fire-and-forget 품질 평가(asyncio.create_task)에서 예외가 유실될 수 있음
- 근거: chat_service.py:527, quality_service.py:93

2. 확장성 문제점
================================================================================

(1) DB 커넥션 병목 (Critical)
- 매 요청마다 PostgreSQL 커넥션 생성/해제
- 동시접속 100명만 되어도 커넥션 폭주 예상
- psycopg의 동기 connect()가 asyncio 이벤트 루프 블로킹
- 해결: psycopg의 AsyncConnectionPool 또는 asyncpg + 커넥션 풀 도입
- 근거: postgres.py:37

(2) LLM API 호출 수 폭증
- 1회 채팅에 최소 2-3회 LLM 호출:
  a) 호감도 분석 (gpt-4o-mini): chat_service.py:272-277
  b) 메인 응답 생성 (gpt-4o/mini): chat_service.py:482-487
  c) quick_score 게이트 (gpt-4o-mini): chat_service.py:495-496
  d) 재생성 시 +1회: chat_service.py:498-503
  e) 백그라운드 품질 평가 (gpt-4o-mini): quality_service.py:55-59
- 10메시지마다 추가:
  f) 대화 요약: memory_service.py:143-151
  g) 팩트 추출: memory_service.py:185-190
  h) 메모리 추출: chat_service.py:412-414
  i) 에피소드 추출: chat_service.py:416-418
- 동시 사용자 증가 시 OpenAI rate limit 도달 가능성 높음

(3) ChromaDB 단일 인스턴스
- PersistentClient로 로컬 파일시스템에 저장 (vector_store.py:37)
- 서버 스케일아웃 시 각 인스턴스가 별도 Chroma 데이터를 가짐
- 해결: Chroma 서버 모드 또는 Qdrant/Weaviate 등 클라이언트-서버 벡터DB 전환
- 근거: vector_store.py:36-37

(4) 대화 히스토리 전체 전송
- ChatRequest에 conversation_history를 클라이언트가 매번 전체 전송 (models.py:36)
- 대화가 길어지면 요청 페이로드가 수 MB까지 증가 가능
- 네트워크 비용 + 서버 파싱 비용 증가
- 해결: 서버 측 대화 히스토리 저장 + room_id 기반 조회

(5) metric_events 테이블 무한 증가
- 모든 이벤트를 단일 테이블에 적재 (postgres.py:90-98)
- 파티셔닝, TTL, 아카이빙 전략 없음
- 근거: postgres.py:90-98, metrics_service.py

3. 기술 스택 적절성 평가
================================================================================

[적절한 선택]

- FastAPI: 비동기 지원, 자동 API 문서, Pydantic 통합 우수. 적합.
- Pydantic v2: 모델 유효성 검사, 직렬화 성능 우수. 적합.
- PostgreSQL 16: JSONB 지원, 안정성, 확장성. 적합.
- ChromaDB: MVP/초기 단계 RAG용으로 적합. 대규모 시 전환 필요.
- Firebase Auth: 모바일 인증 표준. 적합.
- Hilt (Android DI): Google 공식 DI. 적합.
- Room (Android DB): Jetpack 표준 로컬 DB. 적합.
- OkHttp SSE: 안드로이드 SSE 클라이언트로 적합.

[개선 필요]

- psycopg (동기): psycopg[async] 또는 asyncpg로 전환 필요
  - 현재 동기 드라이버가 async 서버의 성능을 저해
  - 근거: requirements.txt:11 (psycopg[binary]==3.2.3)

- ChromaDB 로컬 모드: 프로덕션에서는 서버 모드 또는 관리형 벡터DB 필요
  - 근거: vector_store.py:37 (PersistentClient)

- Moshi (Android): Kotlin Serialization으로 전환 고려
  - KotlinJsonAdapterFactory는 리플렉션 기반으로 느림
  - 근거: AppModule.kt:89-91

- slowapi (Rate Limiting): 단일 인스턴스용. 분산 환경에서는 Redis 기반 필요
  - 근거: main.py:74

[스택 버전 관리]
- requirements.txt에 주요 라이브러리 버전이 고정되어 있어 양호
- httpx<0.28 같은 상한선 제약이 있는 것은 좋은 관행
- 근거: requirements.txt


================================================================================
4. 마이크로서비스 vs 모놀리식 적합성
================================================================================

[현재 상태]: 모놀리식 (단일 FastAPI 앱)

[평가]: 현재 단계에서 모놀리식이 적합함

이유:
1. 팀 규모가 작고 (개인/소규모 프로젝트로 추정) 서비스 간 통신 오버헤드 불필요
2. 배포 단순성이 중요한 초기 단계
3. 서비스 간 데이터 공유가 빈번 (chat_service -> memory_service -> vector_store)
4. Docker Compose로 서버 + DB 2개 컨테이너만 운영

[향후 분리 시점 & 전략]

Phase 1 (현재 ~ 사용자 1,000명): 모놀리식 유지
- 내부 모듈 경계를 더 명확히 정리
- 인터페이스/프로토콜 기반 의존성 역전 적용

Phase 2 (사용자 1,000 ~ 10,000명): 선택적 분리
- 이미지 생성 서비스를 별도 워커로 분리 (비용이 높고 비동기 처리)
- 파인튜닝 서비스를 별도 워커로 분리 (배치 처리)
- 메시지 큐(Redis/RabbitMQ) 도입

Phase 3 (사용자 10,000명+): 핵심 서비스 분리
- Chat Service (LLM 호출)
- Memory Service (요약/추출)
- Vector Search Service (RAG)
- Quality Service (평가)
- API Gateway 도입

[주의사항]
- 조기 마이크로서비스 전환은 운영 복잡성만 증가시킴
- "Modular Monolith" 패턴을 먼저 적용하는 것을 권장
- 근거: 전체 서버 코드 구조 분석

5. 보안 취약점
================================================================================

(1) 콘텐츠 필터 완전 비활성화 (Critical)
- content_filter.py: check_content()가 항상 True 반환
- 유해 콘텐츠가 필터링 없이 LLM에 전달됨
- AI 응답 필터도 비활성화 (chat_service.py:510-519)
- 프롬프트 인젝션 공격에 무방비
- 근거: content_filter.py:19-30

(2) CORS 와일드카드 (High)
- development 환경에서 CORS_ORIGINS = ["*"] (config.py:22)
- production에서 CORS_ORIGINS 미설정 시 빈 리스트지만
  ENVIRONMENT 변수 미설정 시 development 기본값 -> 와일드카드
- 근거: config.py:16-22

(3) 인증 우회 가능 (High)
- REQUIRE_AUTH=false (development 기본값)에서 모든 엔드포인트 인증 없이 접근 가능
- 배포 시 환경변수 누락하면 인증 없이 운영될 수 있음
- 파인튜닝, 이미지 생성 등 비용이 드는 엔드포인트가 무방비
- 근거: auth_middleware.py:30-33, config.py:25

(4) API 키 관리 (Medium)
- OPENAI_API_KEY가 환경변수로만 관리 -> 유출 시 즉시 피해
- API 키 로테이션 메커니즘 없음
- firebase-admin 크레덴셜 파일 경로가 환경변수로 노출
- 근거: config.py:6, .env.example

(5) SQL 인젝션 방지 (Low - 양호)
- psycopg의 파라미터 바인딩을 사용하여 SQL 인젝션 방지
- 단, init_postgres_schema()의 DDL은 하드코딩 (영향 없음)
- 근거: postgres.py:145-168

(6) 입력 크기 제한 부족 (Medium)
- conversation_history에 최대 크기 제한 없음
- 악의적으로 수천 개의 히스토리 메시지를 전송하면 서버 과부하
- memories 리스트에도 크기 제한 없음
- 근거: models.py:36, 43

(7) Rate Limiting 우회 가능 (Medium)
- slowapi가 IP 기반 (get_remote_address)
- 프록시/VPN으로 쉽게 우회 가능
- 인증된 사용자 기반 rate limiting이 아님
- 근거: main.py:74

(8) 파인튜닝 모델 파일 보안 (Medium)
- finetune_models.json이 로컬 파일시스템에 평문 저장
- 모델 ID 조작 시 다른 사용자의 파인튜닝 모델 사용 가능
- 사용자별 접근 제어 없음
- 근거: finetune_service.py:20-51

[보안 개선 우선순위]
1. 콘텐츠 필터 활성화
2. 인증 강제 적용 + 사용자별 rate limiting
3. conversation_history, memories 크기 제한
4. CORS 프로덕션 설정 강제
5. API 키 관리 체계 도입 (Vault 등)

6. 인프라 개선 방안
================================================================================

(1) 배포 파이프라인 부재 (현재 docker-compose만 존재)

현재 상태:
- docker-compose.yml로 로컬 개발환경만 구성
- server 컨테이너가 매번 pip install 실행 (docker-compose.yml:14)
- CI/CD 파이프라인 없음
- 근거: docker-compose.yml

권장 개선:
a) Dockerfile 작성 (멀티스테이지 빌드)
   - pip install을 이미지 빌드 시 수행
   - 레이어 캐싱으로 빌드 시간 단축

b) CI/CD 파이프라인 (GitHub Actions 권장)
   - PR: 린트(ruff/mypy) + 단위 테스트 + API 테스트
   - main 머지: Docker 이미지 빌드 + 레지스트리 푸시
   - 배포: Cloud Run / ECS / K8s 자동 배포

c) 환경 분리
   - dev / staging / production 환경 분리
   - 환경별 설정 파일 관리

(2) 모니터링 & 관측성 부재

현재 상태:
- logging.basicConfig(level=logging.INFO) 기본 로깅만 존재
- metric_events 테이블에 이벤트 기록하지만 시각화 없음
- APM(Application Performance Monitoring) 없음

권장 개선:
a) 구조화된 로깅 (structlog 또는 python-json-logger)
b) APM 도입 (Sentry, Datadog, 또는 OpenTelemetry)
c) 메트릭 수집 (Prometheus + Grafana)
   - 요청 레이턴시, LLM 호출 시간, DB 쿼리 시간
   - 호감도 변화 분포, 품질 점수 추이
d) 알림 설정 (에러율 급증, LLM API 실패, DB 커넥션 고갈)
e) 헬스체크 강화 (현재 /health가 단순 ok 반환, DB/LLM 연결 확인 필요)

(3) 데이터 백업 & 복구

현재 상태:
- PostgreSQL 데이터가 Docker volume에만 저장
- ChromaDB 데이터가 로컬 ./chroma_db에 저장
- 백업 전략 없음

권장 개선:
a) PostgreSQL: 자동 백업 (pg_dump cron 또는 관리형 DB 사용)
b) ChromaDB: 정기 스냅샷 + 클라우드 스토리지 백업
c) 재해복구(DR) 절차 문서화

(4) 테스트 부재

현재 상태:
- 서버/안드로이드 모두 자동화된 테스트 코드 없음
- evaluate.py가 있으나 CI 통합 안 됨

권장 개선:
a) 단위 테스트: 호감도 계산, 프롬프트 빌드, 파싱 로직
b) 통합 테스트: API 엔드포인트 (TestClient 활용)

7. LLM 비용 최적화 전략

[현재 비용 구조 분석]

1회 채팅당 LLM 호출 (최소 3회, 최대 6회):
- 호감도 분석: gpt-4o-mini, ~50 tokens -> ~$0.00002
- 메인 응답: gpt-4o, ~2000 tokens (시스템 프롬프트가 큼) -> ~$0.02
  또는 gpt-4o-mini -> ~$0.0006
- quick_score: gpt-4o-mini, ~100 tokens -> ~$0.00004
- 재생성 (40% 미만 시): gpt-4o, ~2000 tokens -> ~$0.02
- 백그라운드 품질 평가: gpt-4o-mini, ~200 tokens -> ~$0.00008

10메시지마다 추가:
- 대화 요약: gpt-4o-mini, ~800 tokens -> ~$0.0003
- 팩트 추출: gpt-4o-mini, ~500 tokens -> ~$0.0002
- 메모리 추출: gpt-4o-mini, ~500 tokens -> ~$0.0002
- 에피소드 추출: gpt-4o-mini, ~600 tokens -> ~$0.0003

야간 세션 종료 시: 일기 생성 gpt-4o, ~1000 tokens -> ~$0.01
이미지 생성: gpt-image-1, ~$0.04/장 (표정 세트 15장 -> ~$0.60)

[비용 최적화 전략]

(1) 시스템 프롬프트 압축 (즉시 적용 가능, 30-40% 절감 예상)
- 현재 build_system_prompt()가 매우 긴 프롬프트 생성 (~2000+ tokens)
- Few-shot 예시, 호감도 행동 지침, 대화 규칙 등이 매번 전송
- 개선: 프롬프트를 핵심만 남기고 압축, few-shot은 파인튜닝으로 대체
- 근거: prompts.py:988-1113

(2) 모델 라우팅 고도화 (즉시 적용 가능, 20-30% 절감)
- 현재 _classify_message_complexity()가 단순 키워드 기반 (chat_service.py:77-100)
- 개선안:
  a) 대화 초반 5턴은 무조건 gpt-4o-mini (관계 형성 단계)
  b) 호감도 1-2 단계는 gpt-4o-mini 위주
  c) 호감도 4-5 + 감정적 메시지만 gpt-4o
  d) 파인튜닝 모델이 있으면 우선 사용 (더 저렴)

(3) 호감도 분석 최적화 (즉시 적용, 15-20% 절감)
- 현재: LLM 호출 후 실패 시 키워드 fallback
- 개선: 키워드 방식을 1차로 수행, 점수가 모호한 경우만 LLM 호출
- 대부분의 메시지는 키워드만으로 충분히 판단 가능
- 근거: chat_service.py:374-395

(4) 품질 평가 빈도 조절 (즉시 적용, 10-15% 절감)
- 현재: 모든 응답에 백그라운드 품질 평가 수행
- 개선: 5-10턴마다 샘플링 방식으로 품질 평가
- quick_score는 품질 이력이 좋은 캐릭터/대화에서는 스킵
- 근거: chat_service.py:527-531

(5) 캐싱 전략 (중기, 20-30% 절감)
- 유사한 입력에 대한 응답 캐싱 (시맨틱 유사도 기반)
- 시스템 프롬프트 토큰을 prefix 캐싱 활용 (OpenAI의 cached tokens 할인)
- 메모리 컨텍스트가 변경되지 않으면 캐시 재사용

(6) 파인튜닝 적극 활용 (장기, 50-70% 절감)
- gpt-4o-mini 파인튜닝 -> 짧은 프롬프트로도 동일 품질
- 시스템 프롬프트의 성격/말투/few-shot을 파인튜닝으로 내재화
- 파인튜닝 모델은 프롬프트 토큰을 대폭 줄여 비용 절감
- 근거: finetune_service.py

[예상 비용 시나리오 (DAU 1,000명 기준, 평균 20턴/일)]
- 현재 구조: ~$600-800/일
- 최적화 후: ~$150-250/일 (60-70% 절감)
