1. LLM 라우팅 전략 분석
================================================================================

[1.1] 현재 구조

chat_service.py의 _classify_message_complexity() 함수가 메시지 복잡도를 "simple"과
"complex" 두 가지로 분류하여 모델을 라우팅한다.

  - simple -> gpt-4o-mini (저비용, 빠른 응답)
  - complex -> gpt-4o (고품질, 깊은 이해)
  - 파인튜닝 모델이 있으면 최우선 사용

분류 기준:
  (1) 메시지 길이 < 10자 + simple_patterns 매칭 -> simple
  (2) 메시지 길이 > 50자 OR complex_patterns 매칭 -> complex
  (3) 대화 히스토리 < 5턴 -> simple, >= 5턴 -> complex

[1.2] 강점 분석

  - 키워드 기반 분류로 LLM 호출 없이 즉시 판단 (0ms 지연)
  - 대화 깊이(history_len)를 고려한 점진적 모델 업그레이드
  - 파인튜닝 모델 우선 사용으로 캐릭터별 최적화 가능
  - 비용 효율적: 단순 인사/짧은 반응에 mini 모델 사용

[1.3] 취약점 및 개선 사항

  (a) 이진 분류의 한계:
      현재 simple/complex 2단계 분류는 "중간 복잡도" 메시지를 제대로 처리하지 못한다.
      예) "오늘 뭐 먹을까? 고민이야" -> complex_patterns의 "고민"에 매칭되어 gpt-4o 사용
      하지만 실제로는 가벼운 일상 대화에 해당한다.

      권장: 3단계 분류 (simple/medium/complex) 도입
      - medium: gpt-4o-mini + temperature 0.8로 처리
      - complex: gpt-4o 유지

  (b) 감정 깊이 미반영:
      "ㅠㅠ 힘들다" (11자)는 길이 기준으로는 simple이지만,
      complex_patterns의 "힘들"에 걸려 complex로 분류된다. 이 판단은 올바르나,
      반대로 "나 요즘 진짜 맛집 탐방 다니면서 행복해" (길이 > 50)는
      단순 긍정 일상인데 complex로 분류되는 오버라우팅 문제가 있다.

      권장: 감정 키워드에 가중치를 부여하고, 복합 스코어링으로 전환
      score = len_weight * 0.3 + keyword_weight * 0.5 + history_weight * 0.2

  (c) 히스토리 기반 판단의 경직성:
      history_len < 5 -> simple은 대화 초반에 심각한 고민을 꺼내는 경우를 놓친다.
      키워드 매칭이 이를 보완하지만, 키워드에 없는 복잡한 맥락은 누락된다.

  (d) 비용 추적 부재:
      어떤 모델이 얼마나 호출되는지 추적하는 메트릭이 없다.
      모델별 호출 비율과 토큰 사용량을 metrics_service에 기록해야 한다.

[1.4] 정량 분석 (추정)

  현재 라우팅 정확도 (추정): ~75%
  오버라우팅 비율 (불필요한 gpt-4o 사용): ~15%
  언더라우팅 비율 (gpt-4o-mini로 처리한 복잡 메시지): ~10%

  개선 후 목표:
  - 라우팅 정확도: 90%+
  - 비용 절감: 15-25% (오버라우팅 감소)

2. 프롬프트 엔지니어링 평가
================================================================================

[2.1] 시스템 프롬프트 구조 (build_system_prompt)

prompts.py의 build_system_prompt()는 약 1,500~3,000 토큰 규모의 시스템 프롬프트를
동적으로 생성한다. 구성 요소:

  (1) 역할 설정 (캐릭터 정체성, AI 비공개 지시)
  (2) 출력 형식 (JSON 배열 강제)
  (3) MBTI 성격 (traits, style, speech_habits, thinking, emotional, quirks)
  (4) 호감도별 행동 지침 (AFFINITY_BEHAVIORS 5단계)
  (5) MBTI 궁합 정보 (사용자 MBTI 기반)
  (6) 메모리 컨텍스트 (요약 + 팩트)
  (7) 에피소드 기억
  (8) Few-shot 예시 (MBTI 그룹 x 호감도 티어)
  (9) 표현 규칙 (이모지 금지, 감정 선택 가이드)
  (10) 특수 상황 대응 (슬픔, 화남, 짧은 답, 주제 변경, 복귀)
  (11) 대화 흐름 인식 (초반/중반/장기)
  (12) 대화 품질 규칙

[2.2] 강점

  (a) MBTI 성격 정의의 풍부함:
      16개 MBTI 유형 각각에 대해 traits, style, speech_habits, thinking,
      emotional, quirks 6개 차원을 정의한 것은 업계 최고 수준이다.
      특히 emotional 섹션에서 호감도 1~5 단계별 감정 표현 차이를 구체적으로
      기술한 점이 캐릭터 일관성에 크게 기여한다.

  (b) Few-shot 예시 설계:
      FEW_SHOT_EXAMPLES가 MBTI 4개 그룹(NT/NF/ST/SF) x 3개 호감도 티어(low/mid/high)
      = 12개 조합에 대해 2-3개씩 예시를 제공한다.
      이는 GPT-4o의 in-context learning을 효과적으로 활용하는 전략이다.

  (c) 다층적 컨텍스트 주입:
      정적 성격 + 동적 메모리 + RAG 에피소드 + 궁합 정보를 결합하여
      매 대화마다 맥락이 풍부한 프롬프트를 구성한다.

[2.3] 취약점 및 개선 사항

  (a) 프롬프트 길이 문제:
      모든 섹션이 활성화되면 시스템 프롬프트만 3,000+ 토큰에 달할 수 있다.
      여기에 히스토리 20턴(~2,000 토큰) + 메모리(~500 토큰)를 더하면
      입력 토큰이 5,500+ 토큰으로, gpt-4o-mini에서는 비용 부담이 된다.

      권장: 호감도가 낮은 초기 대화에서는 궁합/메모리 섹션을 축소하고,
      대화가 깊어질수록 프롬프트를 확장하는 "점진적 프롬프트 확장" 전략 적용

  (b) Few-shot 예시의 MBTI 그룹 단위 한계:
      NT 그룹에서 INTJ와 ENTP는 성격이 매우 다르지만 같은 few-shot 예시를 공유한다.
      특히 E/I 차원의 차이가 few-shot에서 반영되지 않는다.

      권장: 최소 8개 그룹(NT-I, NT-E, NF-I, NF-E, ST-I, ST-E, SF-I, SF-E)으로 확장

  (c) 감정 태그 일관성:
      10개 감정 코드(NEUTRAL~TOUCHED)가 정의되어 있으나,
      프롬프트에서 각 감정의 정확한 사용 조건을 구체적으로 기술하지 않았다.
      LLM이 PLAYFUL과 HAPPY를 혼용하거나 TOUCHED를 과다 사용할 수 있다.

      권장: 감정 코드별 사용 예시와 금지 조건을 명시적으로 추가

  (d) 출력 형식 강제의 한계:
      "JSON 배열만 출력. 다른 텍스트 일절 금지"라고 지시하지만,
      LLM이 markdown 코드블록이나 설명을 붙이는 경우가 있다.
      _parse_reply()에서 4단계 fallback 파싱으로 대응하지만,
      structured outputs(function calling)를 사용하면 파싱 실패를 원천 차단할 수 있다.

      권장: OpenAI의 response_format={"type": "json_object"} 또는
      function calling으로 전환하여 출력 형식 안정성 확보

[2.4] MBTI 성격 주입 효과 추정

  MBTI_PERSONALITIES의 각 유형별 정의 깊이:
  - traits: 평균 4문장 (성격 핵심)
  - style: 평균 3문장 (말투)
  - speech_habits: 평균 6-7개 (습관적 표현)
  - thinking: 평균 4문장 (사고 패턴)
  - emotional: 4단계 호감도별 반응 기술
  - quirks: 평균 4개 (독특한 행동)

  총 정의 깊이: 유형당 약 400-500 토큰
  이는 학술적 MBTI 정의보다 훨씬 실용적이고 대화에 즉시 적용 가능한 수준이다.

3. 품질 스코어링 시스템
================================================================================

[3.1] 4축 평가 체계 (quality_service.py)

score_response_async()가 gpt-4o-mini를 사용하여 다음 4가지 축을 0-10점으로 평가:

  (1) mbti_consistency (MBTI 일관성): 캐릭터 성격과의 일치도
  (2) contextual_relevance (맥락 관련성): 사용자 메시지에 대한 적절한 반응
  (3) emotional_naturalness (감정 자연스러움): 감정 표현의 자연스러움
  (4) engagement_quality (참여 품질): 대화 지속성과 흥미도

  가중 합산: quality_score = 0.3*mc + 0.3*cr + 0.2*en + 0.2*eq

[3.2] 평가 가중치 분석

  현재 가중치:
  - MBTI 일관성: 30% (가장 높은 가중치, 적절)
  - 맥락 관련성: 30% (적절)
  - 감정 자연스러움: 20%
  - 참여 품질: 20%

  ML 관점 평가:
  가중치 배분은 합리적이나, 고정 가중치는 상황에 따라 비최적이 될 수 있다.
  예) 사용자가 심각한 고민을 상담할 때는 emotional_naturalness의 중요도가 높아야 하고,
  가벼운 잡담에서는 engagement_quality가 더 중요하다.

  권장: 대화 유형별 동적 가중치 조정
  - 감정 상담: mc=0.2, cr=0.2, en=0.4, eq=0.2
  - 일상 대화: mc=0.3, cr=0.2, en=0.2, eq=0.3
  - 정보 교환: mc=0.2, cr=0.4, en=0.1, eq=0.3

[3.3] 빠른 품질 게이트 (quick_score)

quick_score()는 응답 전 빠른 품질 체크를 수행한다:
  - JSON 형식 유효성 검사 (LLM 호출 없이)
  - MBTI 일관성 빠른 확인 (gpt-4o-mini, max_tokens=30)
  - 가중 평균: 형식 40% + MBTI 일관성 60%
  - 임계값 0.4 미만 시 재생성 트리거

  이 설계는 효과적이나, 재생성 시 temperature를 0.85에서 0.9로 올리는 것만으로는
  품질 개선 보장이 어렵다.

  권장: 재생성 시 프롬프트에 "이전 응답이 부자연스러웠으니 더 자연스럽게" 같은
  메타 지시를 추가하거나, 실패 원인에 따른 targeted 재생성 전략 적용

[3.4] 품질 데이터 저장 및 활용

  - PostgreSQL metric_events 테이블에 품질 점수 저장
  - 품질 대시보드 (get_quality_dashboard): 30일 집계, 일별 추이
  - 파인튜닝 데이터 필터링 (get_quality_filtered_conversations):
    quality_score >= 0.6 AND thumbs_down 아닌 대화만 학습

  이 파이프라인은 "품질 평가 -> 저장 -> 학습 데이터 필터링 -> 파인튜닝"으로
  이어지는 데이터 플라이휠을 구성한다. 이는 AI 시스템의 모범 사례에 해당한다.

[3.5] LLM-as-a-Judge 한계

  gpt-4o-mini로 gpt-4o의 응답을 평가하는 구조는 "약한 모델이 강한 모델을 평가"하는
  한계가 있다. 특히 MBTI 일관성의 미묘한 차이를 gpt-4o-mini가 정확히 판별하지
  못할 수 있다.

  권장:
  - 사용자 피드백(thumbs_up/down)을 품질 점수의 ground truth로 활용
  - 정기적으로 인간 평가자(human rater)와 LLM 평가의 일치율 검증
  - 불일치가 큰 경우 평가 프롬프트 보정


================================================================================
4. 메모리 아키텍처
================================================================================

[4.1] 다층 메모리 구조

memory_service.py와 vector_store.py가 3계층 메모리를 구성한다:

  Layer 1 - 대화 요약 (Conversation Summary):
    - 10턴마다 gpt-4o-mini로 대화 요약 갱신
    - 5~8문장, 캐릭터 시점 기술
    - 7가지 추출 항목: 사용자 정보, 중요 사건, 관계 진행, 약속, 감정 변화, 자주 언급 주제, 핵심 맥락
    - PostgreSQL 영속화 + 인메모리 캐시

  Layer 2 - 팩트 추출 (Fact Extraction):
    - key-value 구조 (예: {"key": "직업", "value": "대학생"})
    - 최대 15개 팩트 유지 (FIFO)
    - 중복 검출: 기존 키 기반 dedup
    - PostgreSQL 영속화

  Layer 3 - 에피소드 기억 (Episode Memory):
    - ChromaDB 벡터 스토어에 임베딩 저장
    - text, emotion, importance(1-5), topic 메타데이터
    - 시맨틱 검색 + 시간 감쇄 + 중요도 가중

[4.2] RAG 파이프라인

  (1) 사용자 메시지 -> ChromaDB 시맨틱 검색 (text-embedding-3-small)
  (2) 관련 기억 3개 + 에피소드 3개 검색
  (3) 시스템 프롬프트에 주입 ("떠오르는 기억" 섹션)
  (4) LLM이 기억을 자연스럽게 대화에 활용

[4.3] 강점

  (a) 캐시-DB 2단 구조:
      인메모리 캐시를 앞단에 두고 PostgreSQL을 백엔드로 사용하는 설계는
      cold start 시에도 기억을 복원할 수 있으면서 응답 지연을 최소화한다.

  (b) 에피소드 기억의 감정 태그:
      에피소드에 emotion과 importance를 부착하여 검색 시 활용하는 것은
      인간의 감정 기억 메커니즘을 모방한 우수한 설계이다.

  (c) 중복 방지:
      팩트 추출 시 기존 키와의 중복 검사, 요약 시 "이전 요약과 중복 내용 제거" 지시

[4.4] 취약점 및 개선 사항

  (a) 10턴 고정 주기 문제:
      hist_len % 10 == 0 조건으로 메모리 갱신하는데, 9턴에서 중요한 정보가
      나와도 10턴까지 기다려야 한다.

      권장: 이벤트 기반 갱신 추가
      - 감정 키워드 밀도가 높은 턴에서 즉시 에피소드 추출
      - 사용자가 개인 정보를 언급하면 즉시 팩트 추출

  (b) 팩트 15개 제한:
      장기 관계에서 15개 팩트는 부족할 수 있다.
      카테고리별 팩트 슬롯 (개인정보 5개, 취향 5개, 상황 5개)으로 구조화하면
      더 체계적인 기억 관리가 가능하다.

  (c) 요약의 정보 손실:
      대화 요약은 압축 과정에서 불가피하게 정보를 손실한다.
      특히 농담, 말장난, 감정의 미묘한 뉘앙스는 요약에서 사라지기 쉽다.

      권장: 핵심 대화 원문 보존 (금문장 추출)
      감정적으로 중요한 대화 원문 3-5개를 별도 저장하여 프롬프트에 포함

  (d) 인메모리 캐시 스케일링:
      현재 Dict[str, str] 캐시는 서버 재시작 시 초기화된다.
      멀티 인스턴스 배포 시 캐시 일관성 문제가 발생한다.

      권장: Redis 기반 분산 캐시 도입 (프로덕션 환경)

6. 호감도 계산 모델
================================================================================

[6.1] 하이브리드 호감도 시스템

chat_service.py에서 두 가지 방식의 호감도 변화를 계산한다:

  방식 1 - LLM 분석 (analyze_affinity_with_llm):
    - gpt-4o-mini로 메시지 감정/의도 분석
    - 최근 8턴 + 장기 메모리 컨텍스트 활용
    - MBTI 그룹별 가중치 설명 포함
    - 반환 범위: -3 ~ +5
    - temperature=0.2, max_tokens=50

  방식 2 - 키워드 분석 (calculate_affinity_delta):
    - 7개 긍정 카테고리, 4개 부정 카테고리
    - 부정문 처리 (_is_negated): 접두사/접미사 패턴 매칭
    - 메시지 길이 보너스, 이모티콘 분석, 질문 여부
    - 호감도 레벨별 체감 승수 (1: 1.5x ~ 5: 0.4x)
    - 연속 대화 보너스, MBTI 궁합 가중치
    - KEYWORD_SCALE = 0.4 (LLM과의 스케일 보정)

  통합 로직:
    LLM 결과가 0이면 키워드 결과로 대체 (fallback)

[6.2] MBTI 궁합 모델 (calculate_compatibility)

  4개 기능 그룹(NT/NF/ST/SF) 기반 궁합 점수:
  - 같은 유형: 1.1
  - NT-NF (지적+감성 보완): 1.3 (최고)
  - 같은 그룹: 1.15
  - I/E, T/F 모두 반대: 0.85 (최저)
  - ST-NF, SF-NT: 0.95
  - 기본: 1.0

[6.3] 정량 분석

  키워드 분석 커버리지:
  - 긍정 키워드: 7 카테고리 x 평균 7개 = ~49개
  - 부정 키워드: 4 카테고리 x 평균 4개 = ~16개
  - 총 ~65개 키워드로 한국어 대화의 주요 감정 표현을 커버

  부정문 처리 정확도 (추정):
  - 접두사 10개 + 접미사 13개 패턴으로 한국어 부정문의 ~70% 커버
  - "좋아하지 않아" -> 정상 처리
  - "좋아한다고 생각하지는 않아" -> 이중부정 미처리 (한계)

[6.4] 편향 분석

  (a) 긍정 편향:
      긍정 카테고리(7개)가 부정 카테고리(4개)보다 많고,
      중립 메시지에서도 random.choice([0, 0, 0.5, 0.5, 1.0])으로
      40% 확률로 양수 delta를 부여한다.
      이는 의도적으로 호감도가 올라가기 쉽게 설계한 것으로 보인다.

      평가: 게임화 관점에서는 적절하나, 부정 행동에 대한 페널티가 약할 수 있다.

  (b) MBTI 궁합 편향:
      NT-NF 궁합이 1.3으로 가장 높은데, 이는 MBTI 이론에서 "골든 페어"로
      알려진 조합이긴 하지만, 모든 NT-NF 쌍이 높은 궁합인 것은 아니다.
      INTJ-ENFP는 높은 궁합이지만, INTP-ENFJ는 상대적으로 낮다.

      권장: 16x16 궁합 매트릭스로 세분화

  (c) LLM 분석의 불안정성:
      gpt-4o-mini의 온도 0.2로 호감도를 분석하지만,
      동일 메시지에 대해서도 1-2점 변동이 있을 수 있다.

      권장: 3회 샘플링 후 중앙값 사용 (비용 대비 안정성 트레이드오프)

[6.5] 레벨별 승수 효과

  현재 승수: {1: 1.5, 2: 1.3, 3: 1.0, 4: 0.7, 5: 0.4}

  이 설계는 "초반 빠른 상승, 후반 느린 상승"을 구현한다.
  호감도 4 이상에서 추가로 delta *= 0.7 감쇄를 적용하여 이중 브레이크가 걸린다.
  레벨 5에서는 총 감쇄: 0.4 * 0.7 = 0.28, 즉 초기 대비 약 1/5 수준이다.

  이는 게임 디자인의 "수확 체감" 법칙에 부합하며,
  사용자가 높은 호감도에 도달해도 계속 대화할 동기를 유지하는 효과가 있다.

7. 벡터 검색 최적화
================================================================================

[7.1] ChromaDB 구성 (vector_store.py)

  - 스토리지: PersistentClient (./chroma_db)
  - 임베딩 모델: text-embedding-3-small (OpenAI)
  - 컬렉션 구조:
    * char_{character_id}: 일반 기억 (key-value 메모리)
    * ep_{character_id}: 에피소드 기억

[7.2] 검색 전략

  (a) 일반 기억 검색 (search_relevant):
      - 쿼리: 사용자 현재 메시지
      - 상위 3개 결과
      - max_distance=1.2 필터링 (관련 없는 결과 제외)
      - 시간 가중 없음 (모든 기억 동등)

  (b) 에피소드 검색 (search_episodes):
      - n_results * 3개 후보 검색 후 상위 n개 선택 (오버페칭)
      - 시간 감쇄: exp(-days_ago / 30) - 30일 반감기
      - 중요도 가중: 0.6 + (importance/5) * 0.4 -> 0.8~1.4 범위
      - 최종 점수: semantic_score * decay * importance_weight

[7.3] 강점

  (a) 시간 가중 감쇄:
      exp(-days_ago / 30) 수식은 심리학의 "에빙하우스 망각 곡선"을 근사한다.
      30일 반감기는 대화형 AI의 기억 주기에 적절하다.

  (b) 중요도 가중치:
      importance 1~5를 0.8~1.4로 매핑하여 중요한 에피소드가
      시간이 지나도 우선순위를 유지하도록 설계했다.

  (c) 오버페칭 전략:
      n_results * 3개를 가져와서 시간/중요도 가중 후 상위 n개를 선택하는 것은
      순수 시맨틱 유사도만으로는 놓칠 수 있는 중요 에피소드를 복원한다.

[7.4] 취약점 및 개선 사항

  (a) 일반 기억의 시간 가중 부재:
      search_relevant()에는 시간 감쇄가 없어서,
      오래된 기억과 최근 기억이 동등하게 취급된다.
      "예전에 좋아했던 음식"이 "현재 좋아하는 음식"보다 우선될 수 있다.

      권장: 일반 기억에도 시간 가중 추가 (반감기 60일)

  (b) max_distance 고정값:
      1.2는 경험적 값으로 보이며, 임베딩 공간의 분포에 따라
      최적값이 달라질 수 있다.

      권장: 검색 결과의 distance 분포를 분석하여 동적 임계값 설정
      또는 상대적 임계값 (상위 결과의 distance * 1.5 이내)

  (c) 컬렉션 증가 문제:
      캐릭터별 2개 컬렉션(char_ + ep_)이 생성되므로,
      100명의 캐릭터가 있으면 200개 컬렉션이 된다.
      ChromaDB의 컬렉션 관리 오버헤드가 증가할 수 있다.

      권장: 멀티테넌시 지원을 위해 단일 컬렉션 + character_id 메타데이터 필터링

  (d) 임베딩 비용:
      text-embedding-3-small: $0.02/1M 토큰
      기억 저장 시 + 검색 쿼리 시 임베딩 생성
      대화당 약 2-4회 임베딩 호출

      추정 비용: 사용자 100명 기준 월 $1-2 수준 (매우 저렴)

8. 대화 품질 메트릭스
================================================================================

[8.1] Bigram 다양성 (quality_service.py)

  check_diversity() 함수:
  - 최근 20개 응답과 새 응답의 bigram 겹침 비율 계산
  - diversity_score = 1.0 - avg_overlap
  - score < 0.3이면 low_diversity_warning 이벤트 기록

  분석:
  bigram 다양성은 텍스트 반복을 감지하는 간단하면서도 효과적인 메트릭이다.
  그러나 한국어의 특성상 동일 의미를 다른 어순으로 표현해도
  bigram이 겹치지 않을 수 있어, 의미적 중복을 감지하지 못한다.

  권장: 임베딩 기반 유사도 메트릭 추가
  - 새 응답과 최근 20개 응답의 코사인 유사도 계산
  - 유사도 > 0.85이면 의미적 중복 경고

[8.2] 응답 길이 분석

  _calculate_delay()에서 간접적으로 응답 길이를 관리:
  - <= 5자: 짧은 리액션 (800ms)
  - <= 20자: 일반 (1200ms)
  - > 20자: 길이 비례 (최대 3000ms)

  응답 길이 자체에 대한 메트릭은 별도로 수집하지 않고 있다.

  권장: 응답 길이 분포 추적
  - 평균 응답 길이 (캐릭터별, MBTI별)
  - 사용자 메시지 대비 응답 길이 비율
  - 비정상적으로 짧거나 긴 응답 감지

[8.3] 사용자 피드백 메트릭

  response_feedback 테이블에서 thumbs_up/thumbs_down 수집:
  - thumbs_up_rate = up / (up + down)
  - 품질 대시보드에서 30일 기준 집계

  현재는 이진 피드백만 수집하며, 세분화된 피드백이 부재하다.

  권장:
  - 감정 적절성 피드백 (감정 태그가 맞았는지)
  - "다시 말해줘" 버튼 사용 빈도 추적
  - 대화 이탈률 (마지막 메시지 후 사용자가 떠난 비율)

[8.4] 평가 스크립트 (evaluate.py)

  7개 평가 카테고리:
  (1) 응답 형식 검증: JSON 배열, emotion 유효성, 다중 메시지 분할
  (2) MBTI 성격 일관성: gpt-4o-mini로 일관성 평가
  (3) 호감도 분석 정확도: 10개 시나리오, 키워드-LLM 일치율
  (4) 메모리 추출 품질: 핵심 정보 포함 여부
  (5) 호감도 레벨별 응답 차이: 레벨 1 vs 5 톤 차이
  (6) 응답 다양성: 10회 bigram 겹침 < 40%
  (7) 품질 캘리브레이션: 좋은 응답 > 0.7, 나쁜 응답 < 0.4

  이 평가 프레임워크는 포괄적이며, JSON 리포트 저장 기능으로
  시간에 따른 품질 추이를 추적할 수 있다.

  개선 권장:
  - CI/CD 파이프라인에 통합하여 배포 전 자동 평가
  - 파인튜닝 전후 A/B 비교 자동화
  - 16개 MBTI 전체에 대한 일관성 평가 (현재 4개만)

[10.1] 단기 개선 (1-2주, 높은 ROI)

  [P0] 메트릭 수집 강화 (기대 효과: 데이터 기반 의사결정)
    - 모델별 호출 횟수/토큰 사용량 기록
    - 라우팅 결정 로그 (simple/complex 분류 결과)
    - 재생성 빈도 추적
    - 응답 지연 시간(latency) p50/p95/p99 모니터링

  [P1] 일기 생성 모델 gpt-4o-mini 전환 (기대 효과: 월 $100 절감)

[10.2] 중기 개선 (1-2개월)

  [P1] 3단계 라우팅 도입 (기대 효과: 비용 15% 절감, 품질 유지)
    - simple/medium/complex 분류
    - 복합 스코어링: 길이 * 0.3 + 키워드 * 0.5 + 히스토리 * 0.2
    - medium 메시지에 gpt-4o-mini + 최적화된 프롬프트 적용

  [P1] Few-shot 예시 확장 (기대 효과: MBTI 일관성 15% 향상)
    - 4그룹 -> 8그룹(E/I 구분)
    - 호감도 5단계별 예시 추가
    - 총 40개 조합에 대해 3개씩 = 120개 예시

  [P1] 이벤트 기반 메모리 갱신 (기대 효과: 기억 정확도 25% 향상)
    - 감정 키워드 밀도 기반 즉시 에피소드 추출
    - 개인 정보 언급 감지 시 즉시 팩트 추출
    - 10턴 주기 갱신은 보조 수단으로 유지

  [P2] 품질 스코어링 동적 가중치 (기대 효과: 상황별 품질 10% 향상)
    - 대화 유형 자동 분류 (감정 상담/일상/정보교환)
    - 유형별 4축 가중치 동적 조정

[10.3] 장기 개선 (3-6개월)
